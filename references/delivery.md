# 交付物格式与证据规范

## 0. 词表（状态与方法取值，唯一权威，固定值，不新造同义词）

| 工件 / 字段 | 固定取值 | 说明 |
|---|---|---|
| 站点清单 · 存活状态 | 存活 / 非存活 | 仅「存活」行进入站点覆盖；取值语义、判据与记账见 SKILL.md「输入」节（记账另见「速率与预算总表」） |
| 入口清单.csv · 条目状态 | 未验证 / 待批准 / 已验证 / 未确认 | 未验证 = 尚未按判定表落结论（含已发请求而无结论的形态，原因写备注）；待批准 = 响应体挖掘产物，须用户点名后方可验证；已验证 = 判定表已落结论；未确认 = 网络层失败 |
| 入口清单.csv · 方法 | HTTP 方法（GET/POST/PUT/DELETE/PATCH/HEAD/OPTIONS）或协议标记 WSS / SSE；未知标 `?` | WSS/SSE 为通道标记而非 HTTP 方法（标记 WebSocket/事件流类条目）；`?` = 提取时未知 |
| 入口清单.csv · 验证结果 | 未鉴权可读 / 需凭据 / 不在此前缀 | 仅「已验证」条目填写；「未确认」条目留空。**词表例外**：存在性已确认（**状态记已验证**）但三值皆不适用 → 验证结果留空、备注必填——逐码落位与备注串见 phase3 判定表及兜底；「鉴权拦截未覆盖」写备注列、不占验证结果。其余细节差异（业务层校验、响应摘要）写备注列 |
| 下载日志 · 判定 | OK / TRUNCATED / CL_MISSING / CHUNKED / FAILED / HTTP_&lt;状态码&gt;（实际码：3xx / 4xx / 5xx，如 HTTP_403） | safe_fetch 输出（判定文件 = safe_fetch 的 `_fetch_report.json`）；非 OK 且非 CHUNKED 的文件不得用于提取，逐判定处置见本表下方「下载判定处置」 |

**下载判定处置（上表细则）**：

- TRUNCATED / CL_MISSING：数据不完整（准入见上表行）。连接中断型截断在 safe_fetch 在线路径上表现为 FAILED（IncompleteRead 异常、半截不落盘）；TRUNCATED 主要由 .hdr 侧车重建路径产生——处置等价，均记入未闭环清单（需重抓）。
- FAILED：处置同 TRUNCATED / CL_MISSING——记入未闭环清单（需重抓）。
- CHUNKED：chunked 传输无 CL 的传输方式，非缺陷——200 且非空 ⇒ 可用于提取，产物标注「不可校验」，单独计数不进重试；200 且空 body 判 CL_MISSING（与 safe_fetch 实现一致）；非 200 的 chunked 按状态码判 HTTP_3xx/4xx/5xx——判定顺序状态码优先于 CHUNKED（同上实现）。
- HTTP_4xx：响应完整但非成功——错误体/路径回显按存在性证据记入清单并标「来自错误响应」；WAF 拦截页与默认页只记「存在被拦」信号（确定性结果，不重试）；指纹比对不受限（错误页本是指纹来源）。
- HTTP_3xx：重定向异常（跟随则死循环，或跟随后未成功），记录复核，文件不用于提取。
- HTTP_5xx：多为瞬态，重试耗尽时该 URL 对应的入口清单条目状态记「未确认」（若有对应条目——无条目的静态资源仅记下载判定；文件级判定 → 条目级状态的映射；文件本身不用于提取，存在性与指纹处置同 4xx）。

裸词缺省约定：「状态」默认指入口清单条目状态；「判定」默认指下载判定——验证侧一律写「判定表 / 验证结果」。

近义词分工：

- 清单条目一律称**接口**（「端点」仅指服务端侧功能点，如 Actuator 端点、上传端点）；产物名固定**入口清单**，报告 §3「接口清单」= 入口清单的报告视图（同构异名）。
- **验证** = 阶段 3 发请求落判定；**核验** = 线索升级前的确认（clues → leaks）；**复核** = 归档与存疑结论的重新检查；**核对** = 数值/编号对账（跨会话核对、双向对账）。
- 「覆盖」统称统计口径（站点覆盖率）；防护范围语义写「鉴权拦截未覆盖」。
- 两个「高危」：leaks 级别=高（凭据定级）与挖掘风险列「⚠高危」（路径危险词命中，脚本字面）——判定标准不同，勿混。
- 「前缀」= 基址的路径部分，是判定表语境下对「基址」（§1.5）的简称。
- 散文「免鉴权」= 词表值「未鉴权可读」的口语形，落表用词表值。
- 「占位符」默认指路径动态段（`{id}` 形；URL 列的 `{param}` 为示意形）；前缀常量占位符（`{API_HOST}`）另见 phase2 §3。
- 「对账」单用指粗筛/精提对账；高危双向对账专指 leaks ↔ 报告 §1 收尾自检。

## 1. 入口清单 `入口清单.csv`（核心产物=待办清单；报告位置 = 报告 §3 接口清单）

| 列 | 说明 |
|---|---|
| URL | 完整可访问 URL（基址+路径，动态段保留 `{param}` 占位符） |
| 方法 | 方法取值域见 §0；未知标 `?` |
| 参数 | 已知参数名（来源见 phase2 §3「参数名来源」：脚本 参数名/query 列、归档 URL 查询串），未知留空 |
| 来源 | 页面引用 / JS提取 / 运行时捕获 / 响应体提取 / 历史归档 / 移动端提取 / PROBE(自己构造的探测) |
| 站点 | 归属站点（见 §1.5 定义；URL 的 host ≠ 归属——www 站引用 api.example.com 这类兄弟域接口时归属仍是 www） |
| 状态 | 条目状态，取值见 §0 词表 |
| 验证结果 | 验证结果，取值见 §0 词表 |
| 备注 | 业务归属、鉴权线索、后续测试方向 |

规则：
- 每条必须能回答来源；自己构造的探测标 PROBE，**不与真实接口混排**。
- **形态与通道的分工**：值标签叫**形态**（与脚本输出 `形态=X` 一致，如 形态=hidden:uploadUrl——hidden 系脚本实际输出 `hidden:<变量名>` 前缀变体，无裸 `hidden` 值），形态的类目统称**通道**（通道直方图、粗筛/精提对账按通道计数）。提取器形态 → 来源列映射（写死，不靠语义对号）：

| 形态 | 来源列 |
|---|---|
| `html` | 页面引用 |
| `url / tpl / concat / json / css / fetch / call / ws / sse / wss-url / graphql-op / absolute` | JS提取（方法列自带 WSS/SSE 标记，absolute 自带域外标注（= 第三方域/兄弟域，词形按硬性规则 6）） |
| `hidden:<变量名>` 前缀形态 | JS提取（hidden 系按前缀匹配，仍是写死规则） |
| apk/ipa 静态提取 | 移动端提取 |

**备注列保留具体形态字样**（json/html/css/concat）。
- **多站点分次产物的合并规则**（每站一个 extract CSV 并入入口清单时；**机械执行 = `scripts/build_entry_list.py`**——本节规则是其规格，历轮实弹评测中执行者现写胶水脚本两次出事故，禁止再手搓）：
  - 去重键 = (URL, 方法)。同键跨站并为一行：站点取首个发现站，备注记"亦见于 &lt;他站&gt;"。
  - 状态取信息更全者（已验证 &gt; 待批准 &gt; 未验证 &gt; 未确认）。
  - 两条已验证结果冲突 → 状态改已验证、验证结果记首个、备注标"跨站结果不一致，疑构建漂移"（本身是有价值的发现）。
  - PROBE 行（probe_verify --csv）来源=PROBE、状态=未验证、验证结果留空——判定表落位是执行者动作，脚本不代落结论；探测响应证据（状态/字节/落盘编号）进备注。
  - 页面路由升级（词表例外，§0）：形态=页面引用且请求路径在 safe_fetch `_fetch_report.json` 中判定 OK → 状态=已验证、验证结果留空、备注记存在性证据；路径匹配用报告行的 url 字段归一化对比（落盘文件名含父目录前缀变换，按文件名猜必错——实测事故）。
- **合并完整性对账（机械执行）**：各站点精提 CSV 的每条路径必须在合并后的入口清单在场——`python scripts/reconcile_list.py --fine <每站精提CSV…> --entry 入口清单.csv`；缺失即交付缺陷（人工汇编丢行是实测事故形态：清单少行而报告反查索引仍在引用），退出码 1 供链式拦截；反向（清单有、精提无）只带来源提示——PROBE/运行时捕获/响应体提取/历史归档/移动端提取是精提之外的合法来源。
- 未验证条目是**待办**：滚动补测或明确标注跳过原因（需凭据/属写操作/超范围）。
- 报告里的计数必须是工具输出，禁止人脑估数。
- 置信度由来源列推导，不另设词表：两源重合（静态路线+运行时路线）> 单源 > 归档/推断。归档与单引擎独有条目在备注标"待复核"。

## 1.5 其余产物 schema（自动消费的列契约；「报告位置」列 = §2 报告模板的节号，**不是本文件的节号**——引用约定见 §2）

| 产物 | 报告位置 | 列（依次） | 备注 |
|---|---|---|---|
| `fingerprints.csv` 指纹表 | 报告 §2 资产与指纹 | 组件, 版本串, 依据来源, 证据, 站点 | 依据来源 = 规则库 / 响应头 / Cookie / 错误页 / 规则正则；证据 = 命中的响应文件与头（用规则库时含库名与 commit）；版本以响应原文为准 |
| `leaks.csv` 泄露点清单 | 报告 §4 信息泄露点 | 级别, 类别, 内容, 上下文, 来源文件, 站点 | 级别 = 高 / 中 / 低——高 = 有效凭据可直接使用（云 AK/SK、私钥、DB 连接串、未鉴权敏感数据），或形状确凿的疑似凭据（有效性未验证，备注注明——live/dead 属边界不测）；中 = 需组合利用（JWT、内网 IP、签名逻辑、wss 端点）；低 = 公开标识类（只入低级别，备注标公开标识——公开标识判定规则见 phase2 §6）；**未鉴权敏感数据的定级锚定「可信记录数」**——total 去重、去占位值（13800138000 类连号占位号/测试词）、过格式校验后的条数 + 逐条样本证据，**不锚定 total 或字段填充率**（实测：填充率 95% 而真实率 40%，近半是占位号；schema 字段名是结构信息不是数据值——定低）；内容打码按长度分级：≥10 保留前 4 后 4，6–9 保留前 2 后 2，<6 全遮（短串前4后4等于全露）；类别 = AK/SK、JWT、内网 IP、签名逻辑、SaaS app_id、DB 连接串、wss 端点等 |
| `clues.csv` 注释线索清单 | 核验后并入 报告 §4（线索期不在报告） | 类别, 内容, 置信, 上下文, 来源, 重复次数, 站点 | 与 `scan_comments.py` 的 CSV 输出列**逐字一致**（脚本为权威出处，`--site` 传入）；核验后才升级进泄露点清单——核验 = 上下文人工确认（零请求）+ 必要时按普通候选进阶段 3 验证（授权 ③、占验证预算），无独立请求类别 |
| 高危发现 | 报告 §1 结论摘要 | 非独立产物 | 见下 |

**站点列定义（入口清单 / fingerprints / leaks / clues 四产物共用；后文各处的「归属」即指本列取值）**：值 = 站点清单（来源与口径见 SKILL.md「输入」节）中的**存活站点**——即阶段 2 的覆盖单位，与报告"站点覆盖 M/N"同单位；非标端口站点记 `host:port`。与入口清单"基址"的区别：基址是接口的 API 前缀根（一个站点可挂多个基址，一个基址也可服务多个站点），站点是**资产归属单位**。多站点测绘时来源文件名会撞名（两个站点都有 app.js），站点列是唯一归属维度——**为空即交付缺陷**。

**归属在生成时打标，不事后补填**：脚本产物经 `--site` 透传（extract_endpoints / scan_comments / mine_responses，多站点按站点目录分次运行各传各的）；手工产物（fingerprints / leaks）在处理该站点的当口登记——多站点几百行靠记忆回补必错，这正是来源文件撞名同一类事故。

**移动端与本地目录条目的归属取值**：移动端三态——站点直链下载的 apk → 该站点；应用商店元信息 → 主域（备注标"商店来源"）；用户提供的包 → `-` 且备注写明提供者。本地目录未口述归属 → `-` 且备注写明目录来源。无归属要显式，不留空。

**高危发现的双向定义（当且仅当，不是任一侧）**：`leaks.csv` 级别=高 ⇔ 报告 §1 有对应条目。级别=高 是**证据行**，报告 §1 条目是**上报落点**（发现即报，细则见 §3）——只在 leaks 不在 报告 §1 = 没报；只在 报告 §1 不在 leaks = 报了没证据。收尾自检：**leaks 高行数 == 报告 §1 高危条目数**，不等即为交付缺陷。仍不另设第三份文件。

产物按本表列名消费，不猜。**中间产物 CSV 不入本表契约**：`extract_endpoints --csv` 与 `mine_responses --csv` 以脚本输出列为权威出处（消费前先看表头或脚本 help）；`clues.csv` 因须与报告核验流程逐字对齐才单列契约。

## 2. 测绘报告 `测绘报告.md`

**节号引用约定**：本模板的节号在全文引用时一律写作「报告 §N」；delivery 自身章节写作「delivery §N」——两套编号不同义（如 delivery §3 = 证据规范，报告 §3 = 接口清单），混用时以此区分。

固定结构：

```
# <目标> 测绘报告
## 0. 授权边界声明   （范围 / 未触及 / 操作性质 / 是否触发拦截 / 留痕位置，表格）
## 1. 结论摘要       （编号列表，每条一句话+指向证据，可附后续方向一句话；高危发现在此出现）
## 2. 资产与指纹     （子域名清单摘要 + 组件指纹表 + 站点覆盖 M/N 及未覆盖原因）
## 3. 接口清单       （按业务模块分组；两个率分开标——
                      接口实测率 = 阶段3已验证 / 阶段2提取（限已覆盖站点）；
                      站点覆盖率 = 阶段2已覆盖 / 存活站点数，见 报告 §2）
## 4. 信息泄露点     （每条附上下文证据；高危标注级别）
## 5. 未闭环清单     （未验证入口 / 跳过项及原因 / 存疑结论 / 信息缺口：子域来源是否单一、端口覆盖度、未覆盖站点）
```

## 3. 证据规范

- **每条结论指到一次真实请求**（抓包工具里的 flow/请求编号，或落盘的编号响应文件）。指不到的标「推断，未验证」。
- 关键发现的落盘三件套：`<编号>.body` + `<编号>.headers` + `<编号>.sha256`（校验和文件，防篡改质疑——「侧车」一词专指 .hdr）。编号 = `verify/` 内按站点递增的整数（001 起，跨会话不重置——重置即破坏窗口核对）；请求时间戳记于 `.headers` 首行（跨会话窗口合计按时间戳，编号做唯一键）。手工保存的 curl/代理导出证据用 `probe_verify.py --register-manual` 折进编号体系（完整响应原文自动剥头解析状态码；时间戳回退链 --timestamp > Date 头 > 文件 mtime；原文件不动）——不折编的手工文件不满足首行格式，会触发窗口护栏「时间戳不可读按窗口内计」的保守计数。
- 关键发现给出**最小复现**：一条可重放的请求描述（方法+URL+关键头），他人按此能复核。
- 响应字节数与复测一致 ⇒ 写明"稳定复现"；不一致 ⇒ 标"偶发，待复核"。
- 阴性结论也是产出：某类泄露"0 命中"、某请求"未触发拦截"都如实记录，防止后续重复劳动。
- 报告中出现的凭据/密钥样例打码按 §1.5 leaks 行的长度分级规则执行，全文可 grep 复核无完整凭据。
- 高危发现（未鉴权敏感数据、密钥泄露）**发现即报**，不等报告写完。

## 4. 诚实性条款

- 修正过程写进报告（哪条结论改过、依据是什么）——这是可信度的来源。
- 三分类并列呈现：**已证实 / 已否定 / 跳过**。只报已证实会让人以为其余没问题。
- 启发式产物（推断的用途、导出名含义）标注"已提取 ≠ 已校验"。

## 5. 边界（只记录，不展开）

以下超出本技能「提取接口 + 敏感信息」的职责，发现相关信号只如实记入产物或报告未闭环清单，不展开验证：接管验证、密钥 live/dead 验证、写入 / 越权 / 注入测试、SaaS 悬挂验证。具体红线的阶段展开见 phase2 §6/§8 与 phase3「红线」节。
